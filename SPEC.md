# SPEC — Wolf Tower (Android first)

Цель: приложение, которое снимает DPI-блокировки для WhatsApp, Telegram и сервисов Google/YouTube.
Платформы: Android (этап 1), Windows и macOS (Electron, этап 2-3).

## Архитектура Android
- profiles/profiles.json — общий для всех платформ список сервисов, доменов, пакетов и стратегий.
- ByeDPI (third_party/byedpi, MIT, вендорен в репозиторий, коммит ba53229) собирается через CMake как исполняемый файл libciadpi.so
  и запускается из nativeLibraryDir как отдельный процесс (SOCKS5 на 127.0.0.1:1080).
- DpiVpnService (VpnService) поднимает TUN, маршрутизирует в него ТОЛЬКО пакеты включённых сервисов
  (addAllowedApplication), трафик TUN отдаётся tun2socks, а тот шлёт его в SOCKS5 ByeDPI.
- tun2socks: hev-socks5-tunnel (MIT, вендорен, коммит 50d7b41), отдельный Gradle-модуль :tun2socks (ndk-build),
  мост — HevTun2Socks.kt. Конфиг hev пишется в filesDir/hev.yml при запуске.
- UDP/QUIC: ByeDPI поддерживает UDP ASSOCIATE (флаг -U его запрещает). Если у ВСЕХ включённых профилей
  block_quic=true, сервис добавляет -U: QUIC быстро падает и YouTube откатывается на TCP.
  Если включён WhatsApp (звонки по UDP), -U не добавляется.

## Решения
- Своя стратегия на каждый сервис: ByeDPI запускается с группами опций `--hosts :домены <стратегия> --auto=none ...`.
  Группа срабатывает по SNI, остальной трафик идёт без изменений. Для сервисов, которые подключаются по IP
  без SNI (клиент Telegram), добавляется отдельная группа `--ipset :диапазоны` (ip_ranges в profiles.json;
  список взят по памяти, сверить с https://core.telegram.org/resources/cidr.txt). Фильтры внутри группы
  работают по "И", поэтому домены и IP идут разными группами.
- Диагностика (Diagnose.kt): если у сервиса 0 успехов, проверяется мимо ByeDPI: DNS телефона и DoH, TCP до IP,
  TLS с именем. Показывает, похоже ли на блокировку по IP, подмену DNS или блокировку по SNI.
- Автоподбор (AutoProbe.kt): по 4 варианта стратегии параллельно, каждый на своём локальном порту;
  проверка = TLS-рукопожатие с проверкой сертификата + HTTP-ответ на тестовых адресах (probe_hosts).
  "none" проверяется первым. Выбор: максимум успехов, при равенстве более ранний в списке.
  Ограничение: проверка не видит замедление потоков уже после рукопожатия.
- Диагностика: CrashInfo сохраняет причину сбоя и показывает её при следующем запуске.
- DNS: hev mapdns (198.18.0.2). Приложения получают фейковые IP, в SOCKS5 уходит имя домена,
  ByeDPI резолвит сам через системный DNS телефона. Если оператор подменяет DNS — нужен DoH (отдельная задача).
- IPv6 пока не туннелируется.

## Открытые вопросы
- Флаги ByeDPI проверены по --help коммита ba53229. Реальную эффективность стратегий проверяет только тест в сети.
- Проверить на реальном телефоне и сети оператора: открывается ли YouTube/Telegram/WhatsApp через туннель.

## Лицензирование
- Офлайн-ключи WT1.<payload>.<подпись> (ECDSA P-256), проверка в License.kt, генератор tools/license/keygen.py.
- Автоматического пробного периода нет: без ключа защита не запускается (проверка в DpiVpnService и в UI).
  Проба = ключ plan=trial с датой окончания и привязкой к устройству (ID = хеш ANDROID_ID).
- ID устройства зависит от ключа подписи APK, поэтому сборки подписываются постоянным ключом (секреты WT_* в GitHub).
- Сверка времени без сервера: ClockGuard.kt берёт заголовок Date у популярных сайтов по HTTPS. Телефон отстаёт
  больше чем на час: ключ удаляется, ставится флаг, повторный ввод блокируется до успешной проверки при нормальных
  часах. Без сети сверки нет (осознанно). Проверки: старт приложения, запуск защиты, активация, раз в 30 минут.
- Публичный ключ: android/app/src/main/assets/license_public_key.txt (по умолчанию заглушка).
- Подробности и ограничения: tools/license/LICENSING.md.

## Проверка доступности (Prober)
- GET / с проверкой, что ответ дочитан до конца или дошёл минимум до 40 КБ (ловит обрыв потока после ~16 КБ).
- Блокировка QUIC (-U) задаётся переключателем в UI; без явного выбора включается, если её хотят все выбранные сервисы.
